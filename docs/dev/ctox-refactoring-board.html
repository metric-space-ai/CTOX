Umgebungsfallen

Jede hat mindestens einmal Arbeit gekostet. Vor dem Schreiben eines Auftrags zu lesen.

claude-fleet kennt kein --include-dirtyDer Hauptcheckout trägt dauerhaft ~155 fremde offene Dateien. Fleet ruft claude-agent ohne die Option auf; alle Aufträge scheitern in null Sekunden. Einzeln über claude-agent --include-dirty <rolle> --brief <datei> starten.
Nach einem CAS-Commit trägt der Arbeitsbaum noch die alten DateienHEAD zeigt die neue Fassung, der Arbeitsbaum die alte — der nächste Commit aus diesem Checkout nimmt alles zurück, inklusive gelöschter neuer Dateien. Fremde Änderungen als Patch herausheben, git checkout HEAD -- <pfade>, Patch mit --3way wieder auflegen.
Index-Diff-Pflicht vor commit-treeEin leerer Commit entsteht lautlos, wenn die Staging-Schleife nichts geschrieben hat. Immer git diff-index --cached --name-only zählen und bei 0 abbrechen.
.git/index.lock kann verwaisen0 Bytes, kein Prozess, und trotzdem blockiert sie stundenlang jedes schreibende Git-Kommando — für alle Sitzungen im selben Checkout. Vor dem Entfernen nachweisen, dass kein echter git-Prozess läuft.
Die Testsuite ist bei voller Parallelität unsicher~50 Tests fallen nur parallel durch: Bad file descriptor, failed to inspect running processes, missing port 1234. Vergleiche immer seriell (--test-threads=1) — und niemals einen parallelen Lauf gegen einen seriellen.
Sitzungsneustarts töten Builds des HarnessZwei vollständige Testläufe sind so verloren gegangen. Lange Builds abgekoppelt starten: nohup … & disown, Ausgabe in eine Datei, Fertigmarke ans Ende.
Worker-Läufe kosten 10–18 GB und werden nie aufgeräumtworkjet behält jeden unmarkierten Lauf; claude-agent runs prune verweigert ohne runs mark … integrated|abandoned. Drei parallele Läufe füllen die Platte in einer Stunde.
ENOSPC bricht mehr als den BuildBei 0 Bytes kann nicht einmal mehr ein Befehlsergebnis geschrieben werden, der Peer-Heartbeat wird unschreibbar, und der Watchdog hält den gesunden Peer für tot (S-01).
Der Server liefert Module aus dem Zustand, Paketdateien aus dem Releaseinstalled-modules/… kommt aus ~/.local/state/ctox/business-os/, die gepackten Assets aus ~/.local/lib/ctox/current/. Wer die falsche Kopie ändert, arbeitet an einer Datei, die niemand ausführt. Prüfen, indem man die Datei über HTTP abruft.
Zwei Installationswegectox upgrade --dev holt remote von Branch main. ctox update apply --source <pfad> nimmt einen lokalen Baum — das ist der Weg, um eigene Fixes ohne Push auf die laufende Instanz zu bringen.
Kimi hat keinen ErsatzRolle review fällt nie automatisch weiter. Bei 403 wird die Review aufgeschoben und ausdrücklich als solche gekennzeichnet — niemals als erledigt ausgegeben. Sol maximal 3 parallel.
