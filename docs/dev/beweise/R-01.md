# R-01 — Warum ist origin/main mit 59 Tests rot? (reine Messung, KEINE Aenderung)

## Belegter Befund (vom Orchestrator gemessen, nicht zu wiederholen)

Auf der unveraenderten Basis, seriell (`--test-threads=1`), fallen **59 Tests**
reproduzierbar durch. Groesste Gruppen: `business_os::mcp_channel` (13),
`business_os::store` (9), `service::service_loop` (6), `mission::tickets` (5),
`execution::models::runtime_control` (5).

Die Liste der 59 Namen liegt unter
`/Volumes/tmp/ctox-pipeline/rot-basis.txt`. Ein Beispiel ist
`business_os::mcp_channel::tests::list_entities_keeps_non_admin_entities_read_only`
— arbeitet in einem `tempdir()`, prueft drei simple Zusicherungen, und faellt
trotzdem durch. Das sieht nicht nach Umgebung aus.

Zusaetzlich: bei voller Parallelitaet kommen ~50 weitere Fehlschlaege dazu, die
allein gruen sind (`failed to run git ls-files: Bad file descriptor`,
`failed to inspect running processes`, `missing port 1234`).

## Auftrag — NUR Messung und Klassifikation, KEIN Fix

1. **Seit wann?** Finde fuer die groessten Gruppen per `git bisect` oder
   gezieltem Auschecken aelterer Commits heraus, ab welchem Commit sie rot sind.
   Ein Datum je Gruppe genuegt; nenne den Commit mit Kurz-Hash und Betreff.
2. **Warum?** Fuer jede der fuenf Gruppen EIN Vertreter im Klartext: die
   tatsaechliche Zusicherung, links/rechts, und die Ursache in datei:zeile.
3. **Klassifiziere alle 59** in genau drei Toepfe:
   - `echte_regression` — der Produktionscode ist falsch,
   - `test_veraltet` — der Code ist absichtlich anders, der Test wurde vergessen,
   - `umgebung` — braucht echte Prozesse, Ports, Netz oder einen sauberen HOME.
   Jede Zuordnung mit einem Satz Begruendung.
4. **Parallelitaet:** benenne die gemeinsame Ursache der ~50 nur-parallel-roten
   Tests. Ist es eine geteilte Ressource, ein statischer Zustand, ein fester
   Port? Nenne datei:zeile.
5. **Reihenfolge:** welche fuenf wuerdest du zuerst reparieren, damit das
   Testtor wieder aussagekraeftig wird? Kurze Begruendung je Position.
